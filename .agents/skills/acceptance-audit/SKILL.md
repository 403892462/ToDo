# 独立验收审计

以独立视角验证已批准需求和证据。此 Skill 只读审计被验收实现；不能直接修复生产代码或实现测试。

## 前置条件

- 当前阶段为 `ACCEPTANCE_AUDIT`；
- 实施计划中的工作项均已完成自身验证；
- 不存在活动执行运行或项目锁；
- 需求、方案、追踪矩阵、风险、独立样例和执行证据均可读取。

前置条件不满足时不得生成 PASS。

## 审计输入

1. 读取 `AGENTS.md`、`docs/phase2-contract.md`、需求基线和验收目录。
2. 读取技术方案、风险登记、双向追踪矩阵、工作项与执行证据。
3. 读取独立审计清单；格式见 [审计契约](references/contract.md)。
4. 独立样例必须位于 `acceptance/fixtures/` 或其他明确独立目录，不得把实现单元测试夹具作为唯一判定依据。

## 只读审计

运行审计控制命令：

```text
node scripts/acceptance-audit.mjs audit <清单.json> <报告.md>
```

审计前后计算清单中受保护生产实现和实现测试的 SHA-256 摘要。摘要变化时审计失败，并记录只读边界违规；不得把修改后的实现当作审计修复。

## 结果判定

- `PASS`：覆盖、风险、契约、最终验证和全部独立样例均通过，且受保护文件摘要不变。
- `FAIL`：任一实现验收项失败；报告必须包含失败验收项、证据、退回执行工作项和复验条件。
- `AUDIT_ERROR`：清单、独立夹具或审计工具自身无法可靠判定；单独记录审计缺陷，不归因于生产实现，也不得批准交付。

失败只记录并通过审计循环退回 `execute-plan`；本 Skill 不修改生产实现、实现测试、业务需求或原执行证据。

## 失败退回与复验

1. 使用 `node scripts/audit-loop.mjs return-failure <FAIL报告>` 受控退回报告指定的执行工作项。
2. 执行角色使用 `start-fix` 创建新的修复运行；只允许修改退回工作项覆盖的实现范围。
3. 修复后运行受影响验证，形成新的 PASS 证据，再使用 `complete-fix` 返回独立验收阶段。
4. 新审计清单必须填写 `previousAuditId`、`repairRunId` 和 `repairEvidence`；缺少任一关联时不得复验。
5. 复验生成新的唯一报告，原 FAIL 不得修改或覆盖。复验结果追加到审计循环历史。
6. 复验再次 FAIL 时，上一轮失败、修复和复验整体归档到 `cycles`，再开启下一轮修复。

具体字段和命令见 [审计契约](references/contract.md)。

## 输出与安全

- 报告使用 `.project/templates/acceptance-audit-report.md`。
- 原审计报告不得覆盖；每次运行使用唯一审计编号和新文件。
- 不记录密钥、完整环境变量或不必要的生产数据。
