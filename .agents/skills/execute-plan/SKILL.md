# 执行计划

此 Skill 用于实施、工作项验证、中断恢复、项目级验证和最小首版交付。

## 首先读取

- 仓库中的 `AGENTS.md`；
- `.project/state.md`、`.project/recovery.md` 以及存在时的 `.project/lock.md`；
- 已批准的需求和验收目录；
- 决策记录和变更记录；
- `plans/plan-first-release.md`；
- 相关源代码、测试和用户已有修改。

## 修改前

1. 确认当前阶段为 `IMPLEMENTATION`、`VERIFICATION` 或 `DELIVERY`。
2. 如果项目锁已存在，检查其运行记录并执行恢复或请求人工处理；不得直接覆盖项目锁。
3. 只选择依赖项均为 `DONE` 的 `READY` 工作项。
4. 创建唯一运行编号和项目锁。
5. 记录预期输入和当前需求基线。

## 工作项执行

1. 读取工作项来源需求及其验收标准。
2. 保留用户已有的无关修改。
3. 只实施选中的工作项及其测试。
4. 不得为了让错误实现通过而修改需求或正确的测试夹具。
5. 如果业务规则错误或含糊，停在 `NEEDS_CONFIRMATION`。
6. 运行工作项声明的验证命令。
7. 在 `evidence/` 或 `.project/runs/` 中记录命令、退出码、结果、修改文件和经过脱敏的错误摘要。
8. 只有验证成功并存在证据引用后，才能标记为 `DONE`。
9. 运行记录持久化后，以原子方式更新状态并释放项目锁。

## 失败与重试

- 测试或构建失败：标记为 `FAILED`，修复后再运行。
- 缺少权限、环境或依赖：标记为 `BLOCKED`。
- 业务决策不明确：标记为 `NEEDS_CONFIRMATION`。
- 只有临时网络错误、限流或超时可以重试；最多三次，并记录每次尝试。
- 结构化输出格式错误时，允许进行一次修复尝试。

## 审计退回修复

- `.project/audit-loop.json` 为 `AWAITING_FIX` 时，只能恢复其中的 `returnWorkItem`，不得顺带修改其他工作项。
- 使用 `node scripts/audit-loop.mjs start-fix <RUN-ID>` 创建独立修复运行和项目锁，不复用原实施运行。
- 修复证据必须包含受影响验证和 `最终结果：PASS`；没有该证据不得执行 `complete-fix`。
- 完成修复后进入 `ACCEPTANCE_AUDIT` 等待独立复验；执行角色不得修改或覆盖原 FAIL 报告。

## 需求变更

已批准的业务事实发生变化时，创建 `CHG-*` 记录，取得人工批准，并把受影响的验收标准和工作项标记为 `INVALIDATED`。重新计划并重新验证这些内容，不得只静默修改代码。

## 项目验证与交付

所有首版工作项均为 `DONE` 后，运行项目唯一验证命令。只有当前验证证据成功，并具备安装和运行说明、输入输出示例、已知限制以及项目负责人完成 Gate 3 批准时，才能交付。

不得仅凭已经生成代码或尚未执行的命令宣称完成。
