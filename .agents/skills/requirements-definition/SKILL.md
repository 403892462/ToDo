# 需求定义

在 Gate 1 已确认问题定义之后、实施计划开始之前，使用此 Skill。

## 首先读取

- `.project/state.md`
- `docs/discovery.md`
- `docs/requirements.md`
- `docs/acceptance-catalog.md`
- `docs/decision-log.md`
- 仓库中的 `AGENTS.md`

当前阶段必须是 `REQUIREMENTS`。不得悄悄把尚未解决的业务假设转换成既定需求。

## 稳定编号

使用：

- `GOAL-*`：业务目标；
- `BR-*`：业务规则；
- `FR-*`：功能需求；
- `NFR-*`：非功能需求；
- `AC-*`：验收标准；
- `DEC-*`：决策；
- `ASM-*`：假设。

已经分配的编号不得重新排序或重复使用。被删除的条目应标记为已废弃。

## 工作流程

1. 把已确认的预期结果转化为业务目标、业务规则和首版需求。
2. 为每条功能需求说明业务目的、前置条件、输入、行为、输出、异常情况、是否属于首版，以及关联的验收标准编号。
3. 使用具体的“给定／当／则”观察结果编写验收标准；涉及公式时，加入具有代表性的业务样例。
4. 单独列出假设。阻塞性假设必须经过人工确认。
5. 检查每条首版功能需求是否至少拥有一条验收标准。
6. 请求项目负责人确认公式、异常处理、范围和完整需求基线。
7. 只有在 Gate 2 批准后，才能记录 `Requirements Baseline v1.0`。
8. 推进阶段前运行项目协议检查器。

## 边界

描述产品必须实现什么，不编写非必要的技术设计。当技术可行性尚不确定时，记录风险或后续验证需求，不得因此擅自改变业务需求。
