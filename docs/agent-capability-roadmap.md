# 受控项目 Agent 能力范围、局限性与优化路线

## 1. 当前能力范围

### 1.1 已具备的核心闭环

当前系统已实现：

- 从业务发现到最终交付的阶段化流程。
- 需求、验收、方案、工作项、测试和证据追踪。
- 人工 Gate 防线。
- 技术风险门和实施计划确认。
- 工作项串行执行、真实验证和中断恢复。
- 唯一下一动作决策。
- 保守并行分组、资源租约和范围漂移停止。
- 独立验收审计与失败退回。
- 基础耗时、质量、用量和成本指标。
- Gate 3 后的交付复盘和建议治理。

### 1.2 适用场景

当前版本适合：

- 单仓库、单负责人或小团队项目。
- 阶段相对稳定、需要人工审批的软件交付。
- 强调需求确认、证据和审计的项目。
- 本地运行、Node.js 脚本可执行的工程环境。
- 工作项可以通过文件和资源范围描述的项目。

### 1.3 不适用或需要谨慎使用的场景

- 大型多仓库、多组织协作项目。
- 需要实时分布式调度的系统。
- Gate 和阶段高度动态且因项目频繁变化的组织。
- 需要法规级电子签名、身份认证和不可抵赖审计的场景。
- 必须依赖 CI/CD、云部署和生产遥测才能完成的交付。

## 2. 当前局限性

### 2.1 Gate 和阶段存在硬编码

当前 `project-orchestrator` 固定认识：

- `GATE_1`
- `GATE_2`
- `UI_GATE`
- `SOLUTION_DESIGN`
- `IMPLEMENTATION_PLAN`
- `GATE_3`

`delivery-retrospective` 也固定要求 Gate 3 批准。

影响：

- 新项目增加 Gate 4 时，系统不会自动识别。
- 不同项目无法仅通过配置调整阶段。
- Skill 文本、解析器、决策器和测试可能需要同步修改。

### 2.2 项目契约仍偏向当前仓库

状态解析依赖当前文档名称、标题和 Markdown 格式。新项目若使用不同文件结构，需要适配代码。

### 2.3 并行调度只做保守判定

当前系统能判断是否建议并行，但不提供成熟的真实 Git 工作树隔离、自动合并和冲突解决。

### 2.4 缺少 CI 集成

验证主要由本地命令触发，没有在远端 CI 中自动复验状态、追踪、测试、构建和审计。

### 2.5 指标覆盖不完整

当前只有部分运行具备有效指标事件，不能准确计算整个周期的总耗时、总 Token 和总成本。

### 2.6 单模型、单审计实现

独立审计在角色和只读边界上独立，但没有多模型交叉判断，也没有模型版本差异分析。

### 2.7 人工确认身份较弱

当前 Gate 使用文档中的确认人和时间，适合本地工程治理，但不等同于强身份认证或电子签名。

### 2.8 周期初始化不够模板化

新项目仍需要人工复制目录、文档和配置，容易出现遗漏或旧项目字段残留。

### 2.9 Markdown 解析容易受格式变化影响

标题层级、中文标点或字段格式改变，可能导致解析失败。失败关闭是安全的，但会增加维护成本。

### 2.10 运行环境覆盖有限

当前主要验证 Windows、PowerShell、Node.js 和本地仓库环境；跨平台兼容尚未形成完整矩阵。

## 3. 推荐优化方向

## 3.1 优先级 P0：配置化阶段与 Gate

这是通用化的首要优化。

新增项目契约配置，例如：

```json
{
  "schemaVersion": 1,
  "stages": [
    "DISCOVERY",
    "REQUIREMENTS",
    "SOLUTION_DESIGN",
    "PLANNING",
    "IMPLEMENTATION",
    "ACCEPTANCE_AUDIT",
    "DELIVERY",
    "PRODUCTION_RELEASE",
    "COMPLETED"
  ],
  "gates": [
    {
      "id": "GATE_1",
      "stage": "DISCOVERY",
      "approval": "HUMAN",
      "required": true
    },
    {
      "id": "GATE_4",
      "stage": "PRODUCTION_RELEASE",
      "approval": "HUMAN",
      "required": true,
      "finalDeliveryGate": true
    }
  ]
}
```

目标：

- 编排器动态读取阶段和 Gate。
- 复盘器读取 `finalDeliveryGate`，不再固定绑定 Gate 3。
- 未知 Gate、重复 Gate、循环阶段和缺失最终 Gate 时失败关闭。
- 当前 Todo 项目通过兼容配置继续使用 Gate 1～3。

## 3.2 优先级 P0：统一契约 Schema

为状态、周期、Gate、工作项、指标、审计和复盘建立 JSON Schema 或等价验证器。

收益：

- 降低 Markdown 格式耦合。
- 更清楚地区分机器事实和人类说明。
- 新项目初始化时可以自动校验。

## 3.3 优先级 P1：模板化项目初始化

提供命令：

```text
agent-project init <项目名称> <契约模板>
```

自动生成：

- 目录结构。
- 状态文件。
- 周期注册表。
- 文档和 Skill 模板。
- 基础测试。
- 唯一验证命令。

初始化只生成草稿，不自动批准任何 Gate。

## 3.4 优先级 P1：CI 只读复验

CI 应执行：

1. 协议检查。
2. Lint 和测试。
3. 构建与冒烟测试。
4. 追踪覆盖检查。
5. 审计夹具格式检查。
6. 敏感信息扫描。

CI 可以验证 Gate 证据，但不能代替人工批准。

## 3.5 优先级 P1：真实 Git 工作树隔离

为允许并行的工作项创建独立工作树或分支，并记录：

- 基线提交。
- 文件范围。
- 工作树标识。
- 验证结果。
- 合并前漂移检查。

发生冲突时停止并转人工处理，不自动选择覆盖策略。

## 3.6 优先级 P1：全周期指标自动采集

每个工作项、审计和交付动作都自动写入指标事件。

需要明确区分：

- 主动工作耗时。
- 等待人工 Gate 的时间。
- 重试和失败次数。
- 测试、构建和审计质量。
- 模型、工具和基础设施成本。

缺失值继续保持未知，不能用估算替代事实。

## 3.7 优先级 P2：多模型审计

可让不同模型对同一独立夹具进行交叉审查，但最终判定必须：

- 保留模型名称和版本。
- 保留输入摘要和结构化结果。
- 明确一致、分歧和不可判定状态。
- 不以“多数投票”掩盖关键失败。
- 继续遵守只读审计边界。

## 3.8 优先级 P2：强身份 Gate 审批

对于高合规项目，可接入：

- 企业身份认证。
- 动态验证码或硬件密钥。
- 带时间戳的签名记录。
- 审批撤销和重新批准规则。

审批凭证不得包含密码、密钥或完整身份敏感数据。

## 3.9 优先级 P2：跨平台与多仓库支持

补充：

- Windows、Linux、macOS 测试矩阵。
- PowerShell 与跨平台 Node.js 控制器一致性。
- 多仓库依赖和版本锁定。
- 跨仓库工作项的原子状态与失败恢复。

## 4. 推荐迭代顺序

建议下一阶段按以下顺序推进：

1. 配置化阶段、Gate 和最终交付 Gate。
2. 统一机器契约 Schema，并保持当前项目兼容。
3. 模板化新项目初始化。
4. CI 只读复验。
5. 全周期指标自动采集。
6. 真实 Git 工作树隔离和并行执行。
7. 多模型审计与强身份审批。

前两项是后续能力的基础，应优先于继续添加硬编码 Gate。

## 5. 后续优化的验收原则

无论增加什么能力，都应保持：

- 人工 Gate 不被自动化绕过。
- 未知信息不被模型自行补全。
- 失败不被标记为成功。
- 审计不修改被审计对象。
- 历史报告和失败证据不可覆盖。
- 建议不自动转化为需求。
- 缺失成本和 Token 不被估算。
- 新能力能够通过独立样例验证。

## 6. 结论

当前 Agent 已具备可靠的单项目工程闭环，优势是状态明确、证据可追踪、失败关闭和人工决策边界清晰。主要短板不是缺少更多自动化动作，而是阶段、Gate、文件格式和运行环境仍与当前项目绑定。

下一步应先把流程规则从代码常量提升为版本化项目契约，再扩展 CI、模板化、多模型和真实并行能力。
