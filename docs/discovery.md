## Phase 3 工程工作流：编排与交付复盘

### 用户原始表述

- “phase 3 搭建 project-orchestrator+delivery-retrospective。”
- “Phase 3 首版核心闭环优先。”
- “允许自动推进非人工阶段，但 Gate 1、Gate 2、UI Gate、实施计划、Gate 3 必须由 dezhi 人工确认。”
- “仅无依赖且文件影响范围不重叠的工作项允许并行，一旦发生冲突立即停止并转人工处理。”

### 已确认事实

- Phase 3 是工程工作流能力建设，不是 Todo 产品业务功能迭代。
- 目标用户是项目负责人 dezhi，以及使用当前受控流程推进项目的执行与审计角色。
- 典型场景是从一个已进入受控流程的项目状态出发，识别下一合法动作、调度工作项、执行确定性检查，并在交付后形成复盘。
- Phase 1 与 Phase 2 已提供需求、方案、规划、执行、独立审计、交付门、状态契约和验证证据；当前缺少统一编排与交付数据沉淀。
- Phase 3 首版采用核心闭环优先，只建设 `project-orchestrator`、`delivery-retrospective`、串行/并行工作项调度和基础成本、延迟、质量指标。
- 编排器允许自动推进无需业务判断的阶段，但 Gate 1、Gate 2、UI Gate（适用时）、技术方案确认、实施计划确认和 Gate 3 必须由 dezhi 人工批准。
- 只有不存在依赖关系、文件影响范围不重叠且公共接口/共享状态不存在语义冲突的工作项才能并行；发现冲突立即停止并转人工处理。

### 当前问题

- 阶段推进、工作项选择、验证和审计虽然已有受控命令，但仍需要人工识别顺序并逐一调用，容易遗漏下一步或错误操作。
- 现有流程不能统一计算工作项的依赖和影响范围，也不能可靠判断哪些工作可以安全并行。
- 交付完成后缺少结构化复盘，无法持续比较实际耗时、失败与重试、验证质量和流程瓶颈。
- 项目已完成后启动下一版本周期缺少正式入口，容易依赖人工修改状态。

### Phase 3 首版期望结果

- 编排器读取现有状态、阶段契约、工作项、依赖、影响范围和验证结果，给出唯一合法的下一动作或明确的等待/阻塞原因。
- 对确定性、非人工阶段，在所有前置条件通过后自动推进；遇到人工 Gate、失败、信息不足或冲突时停止。
- 调度器默认串行；只有满足已确认安全条件的工作项才进入并行组，并持续检查范围漂移和冲突。
- 交付复盘汇总阶段和工作项耗时、失败与重试、验证结果、审计结果以及可获得的使用量/成本信息，输出事实、偏差和改进建议。
- 复盘建议不得自动修改需求、方案、测试、规则或历史证据；采纳建议必须进入下一次受控变更或版本周期。

### 范围内

- `project-orchestrator`：读取项目事实、识别当前阶段、判断下一合法动作、调用现有受控命令、等待人工 Gate、失败关闭和恢复提示。
- 版本周期入口：从已完成项目启动下一版本发现阶段，并保留上一版本完成状态和证据。
- 工作项调度：依赖检查、影响范围声明、默认串行、安全并行分组、冲突停止和人工接管。
- `delivery-retrospective`：从运行、验证、审计和交付记录生成结构化复盘。
- 基础指标：阶段/工作项耗时、成功/失败/重试次数、测试与审计结果、可获得的 token/调用量/成本；无法获得时明确记为“未知”，不得估算成事实。
- Todo 项目作为首个迁移与故障验证样例，同时保持契约可复用于后续项目。

### 明确排除

- 真实多模型审计及模型间裁决。
- GitHub Actions、GitLab CI 或其他真实 CI 平台接入。
- 新项目模板化初始化。
- 真实 Git 分支与 `git worktree` 的创建、合并、清理和冲突解决。
- Todo 产品公网部署、域名、HTTPS 和异地手机访问。
- 编排器绕过人工 Gate、自动接受风险、自动修改验收标准或把失败降级为成功。

### 输入与输出

- 编排器输入：项目状态、阶段契约、已批准产物、工作项依赖与影响范围、运行/验证/审计结果、人工 Gate 状态。
- 编排器输出：下一动作、执行或等待状态、理由、受控命令结果、阻塞/冲突记录和可恢复位置。
- 调度输入：READY 工作项、依赖关系、声明的文件影响范围和共享接口/状态范围。
- 调度输出：串行顺序或安全并行组；不安全时输出具体冲突并停止。
- 复盘输入：阶段时间、运行记录、验证证据、审计报告、交付记录和可获得的使用量元数据。
- 复盘输出：结构化事实、计划与实际偏差、质量结果、成本/延迟摘要、问题归因和待负责人决定的改进建议。

### 可观察成功标准

- 在固定项目夹具上，编排器只能选择契约允许的下一动作；人工 Gate 未批准时不得继续。
- 自动检查、测试或审计失败时，编排器保留失败证据并停止，不得把阶段标记为完成。
- 调度器对有依赖、文件重叠或共享接口冲突的工作项拒绝并行，对满足全部条件的工作项生成稳定一致的并行分组。
- 执行中出现未声明的范围漂移或冲突时，相应并行组停止并生成可定位记录。
- 完成交付后可生成一份可追溯复盘，其中耗时、失败、重试、验证和审计结论均能链接到来源；缺失成本数据明确显示为未知。
- 复盘建议不会直接改变任何已批准事实，只有负责人批准后才进入下一版本。

### 负责人、数据和不可逆操作

- 业务规则、人工 Gate、冲突处理及复盘建议采纳的最终负责人：dezhi。
- 首版只处理项目元数据、源代码路径、状态、测试与证据；不得记录密钥、完整环境变量、不必要的生产数据或第三方模型输入正文。
- 外部系统仅限现有本地文件系统、PowerShell、Node.js/npm 和项目验证命令；不新增真实 CI、Git 托管或多模型服务连接。
- 自动阶段推进、并行工作启动和下一版本周期启动均必须留下不可覆盖的操作记录；已生成历史记录不得静默删除。

### 风险与假设

- 无真实工作树隔离时，即使文件不重叠，共享生成文件、状态文件和构建缓存仍可能冲突；首版必须采用保守判定并在不确定时串行。
- 文件范围声明可能与真实修改不一致，因此需要执行中范围漂移检查，不能只在调度前判断一次。
- 不同模型/API 的 token 与费用元数据未必可获得或可比较；首版只记录真实可得数据和“未知”。
- 自动推进会放大错误状态的影响，因此编排器必须复用现有契约检查和失败关闭规则，不自行推断通过。

### 待确认事项

- 阻塞项：无。三项首版范围和自动化边界已由 dezhi 确认。
- 非阻塞项：后续需求阶段需定义基础指标的稳定字段、单位和来源优先级。
- 非阻塞项：后续技术方案需验证在不使用真实 Git 工作树时，并行执行能否满足共享状态与构建缓存隔离；不能证明安全时必须退化为串行。

## Phase 2 工程工作流：质量闭环

### 用户原始表述

- “附件项目的总体架构。”
- “phase 1 搭建 requirements+business+implementation+execute。”
- “phase 2 搭建 solution-design+acceptance-audit。”
- “phase 3 搭建 project-orchestrator+delivery-retrospective。”

### 已确认事实

- 本次 Phase 2 是项目工程工作流能力建设，不是 Todo 产品功能迭代。
- Phase 1 已建立业务发现、需求定义、实施规划、串行执行以及受控阶段门。
- Phase 2 的主题是“质量闭环”，核心新增能力为 `solution-design` 和 `acceptance-audit`。
- Phase 2 同时需要追踪矩阵、风险登记、需求变更影响检查、独立验证样例和自动契约检查。
- Phase 3 才建设 `project-orchestrator`、`delivery-retrospective`、多模型审计、Skill/模型版本兼容、并行工作项与工作树、CI、模板化初始化，以及成本、延迟和质量指标。
- 公网部署继续延期到上述工程工作流建设之后处理。
- 第一版工程流程继续坚持：不静默覆盖、不跳过状态、验证失败时不宣称完成。

### 当前问题

- Phase 1 能把业务想法推进到代码和测试，但缺少正式的技术方案与风险评审层。
- 当前执行结果主要由执行流程自身验证，缺少交付前独立验收、需求覆盖审计和失败闭环。
- 需求、方案、工作项、测试与证据之间已有局部引用，但尚无统一追踪矩阵和自动契约检查。
- 需求发生变化时已有 `CHG-*` 机制，但缺少由工具系统化计算和校验受影响方案、工作项、测试及证据的能力。

### Phase 2 期望结果

- 已确认需求在进入实施规划前，经过 `solution-design` 形成可追踪的技术方案、边界、风险和验证策略。
- 执行完成后、进入交付 Gate 前，由 `acceptance-audit` 独立核对需求覆盖、契约、测试、证据和失败状态。
- 任一需求可追踪到方案、工作项、测试与证据；任一实现工作项也可反向追踪到已批准需求。
- 需求变化会自动指出并使受影响下游产物失效，不能继续沿用旧的完成状态。
- 独立验证样例与实现测试分离，避免仅通过修改实现自带测试而形成虚假完成。

### 范围内

- 新增 `solution-design` Skill、产物模板、状态规则和阶段门。
- 新增 `acceptance-audit` Skill、独立验收样例、审计报告、失败回退和最终验证规则。
- 建立需求 → 方案 → 工作项 → 测试 → 证据的双向追踪矩阵。
- 建立风险登记，记录风险、影响、缓解措施、负责人和验证状态。
- 扩展 `CHG-*` 变更流程，自动检查需求变更影响并使受影响产物失效。
- 增加自动契约检查，校验编号、引用、状态、阶段门、证据和唯一验证命令的一致性。
- 使用当前 Todo 项目作为首个兼容与回归样例，同时保持流程可复用于后续项目。

### 明确排除

- Phase 3 的统一 `project-orchestrator` 和 `delivery-retrospective`。
- 多模型审计、并行工作项、工作树、CI、模板化新项目初始化和量化成本/延迟指标。
- Todo 产品公网部署、域名、HTTPS 和异地手机访问。
- 在 Phase 2 中重做已经稳定的 Phase 1 技能；只做质量闭环所需的最小兼容调整。

### 可观察成功标准

- 一个已批准需求可以自动追踪到方案、工作项、测试和验证证据，缺失任一必需链接时协议检查失败。
- 一个需求发生变更后，工具能列出受影响方案、工作项、测试和证据，并阻止旧状态继续作为交付依据。
- 执行流程宣称完成但独立验收样例失败时，`acceptance-audit` 必须拒绝交付并留下可恢复状态。
- `solution-design` 中未处理的高风险项会阻止实施规划通过。
- 当前 Todo 项目的既有 Phase 1 产物可迁移或兼容，不因新增流程而被静默标记为失败或完成。

### 输入与输出

- `solution-design` 输入：已批准需求基线、验收目录、UI Gate 结果（适用时）、现有代码与架构约束、变更记录。
- `solution-design` 输出：风险分级、简化或完整技术方案、架构边界、风险登记、验证策略及方案确认状态。
- `acceptance-audit` 输入：已批准需求与方案、实施计划、执行记录、实现测试结果、独立验收样例和验证证据。
- `acceptance-audit` 输出：追踪矩阵覆盖结果、独立验收结果、缺陷与证据、退回目标、复验记录及交付建议。

### 负责人、数据与操作边界

- 业务规则和阶段门最终负责人：dezhi。
- Phase 2 处理项目需求、方案、源代码、测试和证据；不得把密钥、完整环境变量或不必要的生产数据写入方案、矩阵、审计报告和运行证据。
- Phase 2 不新增第三方业务系统；运行继续依赖本地文件系统、PowerShell、Node.js/npm 和项目唯一验证命令。
- 下游状态失效、审计拒绝和工作项退回必须保留历史记录，可通过修复与复验恢复；Phase 2 不提供静默删除或覆盖历史失败的操作。

### 阻塞性待确认事项

- `ASM-018` 状态：CONFIRMED；所有需求变更必须经过 `solution-design` 影响评估；低风险变更可使用简化方案记录，中高风险变更必须形成完整技术方案。涉及数据模型、安全、权限、外部系统、不可逆操作、公共 API 或跨模块修改时，必须执行完整设计；任何简化均需记录理由，不得静默跳过。
- `ASM-019` 状态：CONFIRMED；`acceptance-audit` 不得修改被审计的生产实现或实现测试。审计失败必须保留证据并退回 `execute` 修复，执行流程重新验证后再由审计流程独立复验。审计角色仅可修正自身审计脚本、独立样例或报告中的缺陷，并须单独记录。

### 已确认职责原则

- `solution-design` 采用“强制评估、风险分级、深度不同”的规则，避免小改动被完整方案流程拖慢，同时防止高风险变更绕过设计。
- `acceptance-audit` 与实现修复保持职责分离，不能通过修改被审计实现或其测试让自身审计通过。
- 审计失败记录不可被后续成功覆盖；复验必须引用原失败、修复运行和新的独立审计证据。

### 非阻塞风险

- 在没有 Phase 3 编排器前，Phase 2 仍由现有受控脚本和人工阶段推进串联。
- 追踪矩阵若要求过细会增加维护成本，应优先覆盖业务需求、关键风险、工作项、自动测试和最终证据。
- 独立样例必须避免复用实现内部夹具，否则“独立审计”会退化为重复运行同一批测试。

## 下一版本变更发现：SQL Server 与真实手机访问

> CHG-008 已批准：v1.3 数据库已由 SQL Server 调整为 PostgreSQL；本节中 SQL Server 相关历史表述由该变更覆盖。

### CHG-008 数据库调整

- 下一版本使用 PostgreSQL 持久保存任务，不再使用 SQL Server。
- 匿名个人空间、管理员恢复、同机部署、域名 HTTPS、数据隔离和不迁移旧数据等已确认业务规则保持不变。
- 已确认使用 PostgreSQL 17、用户名密码认证，并与 Next.js 部署在同一台公司服务器。
- 已确认该服务器上已有可连接的 PostgreSQL 17 实例。

### 用户原始表述

- “任务要求保存在 SQL Server 数据库。”
- “要求能在手机端使用。”

### 已确认事实

- v1.2 已完成并独立交付。
- 下一版本必须使用 SQL Server 持久保存任务。
- 下一版本必须支持在真实手机上访问和使用现有核心任务功能。
- 本变更不自动恢复家庭/小组共享、提醒或复盘等已排除能力。
- 支持多个用户使用，但不要求传统账户登录。
- 不同用户的任务数据必须在用户级别隔离。
- 手机必须能够通过互联网异地访问，而非仅限同一局域网。
- 已有可用的 SQL Server 2014 SP3 实例，采用 SQL Server 用户名密码认证。
- 用户身份采用“匿名个人空间 + 高强度访问码”：首次使用自动生成个人空间和访问码，当前浏览器保存访问凭证；换手机时输入访问码恢复个人空间。
- v1.2 浏览器本机旧任务不迁移到 SQL Server。
- 当前没有公网服务器、域名或 HTTPS；下一版本范围必须包含公网部署与 HTTPS 配置。
- SQL Server 位于公司局域网，不具备公网或云网络地址，也不允许从公网直接访问。
- 应用服务器必须通过公司私网连接 SQL Server。
- 访问码丢失且所有已授权浏览器均不可用时，必须支持通过管理员身份验证恢复访问。
- 已批准租用公网服务器、购买域名并承担持续费用。
- 管理员恢复采用单一管理员账号、强密码和动态验证码；管理员按个人空间 ID 重置访问码，新访问码生成后旧码立即失效，并记录恢复时间和操作日志。
- 采用公司内网服务器部署方案：Next.js 应用与现有 SQL Server 安装在同一台公司服务器上；只通过域名和 HTTPS 向互联网发布 Web 服务，SQL Server 端口不开放公网。
- 不再租用独立公网应用服务器；仍需购买域名并承担域名及公网接入相关持续费用。

### 下一版本目标用户与场景

- 多个个人用户通过手机浏览器从互联网异地使用任务管理功能。
- 用户不注册传统账户，以匿名个人空间和访问码识别、隔离及恢复自己的数据。
- 单一管理员负责访问码恢复，不参与普通任务管理。

### 当前问题与预期结果

- 当前任务只保存在单个浏览器，无法在真实手机异地访问，也无法跨设备恢复个人数据。
- 下一版本把任务持久化到 SQL Server，使同一匿名个人空间可在不同手机恢复，并确保不同空间的数据互不可见。
- 公司服务器通过域名和 HTTPS 提供公网 Web 访问，数据库只接受本机或内网连接。

### 范围内

- 匿名个人空间创建、高强度访问码生成、浏览器凭证保存和换手机恢复。
- 所有现有任务读写改为 SQL Server 2014 SP3 持久化，并按个人空间隔离。
- 单一管理员以用户名、强密码和动态验证码验证身份后重置指定空间访问码。
- 重置后旧访问码立即失效，并记录恢复时间和管理员操作日志。
- 公司服务器部署、域名接入和 HTTPS 配置；仅发布 Web 服务。
- 数据库连接凭据和管理员秘密仅保存在服务端安全配置中。

### 明确排除

- 不迁移 v1.2 浏览器本机旧任务。
- 不提供用户名、邮箱或手机号形式的普通用户注册登录。
- 不增加家庭/小组共享、任务分配、到时提醒、复盘统计或删除恢复。
- 不将 SQL Server 端口或数据库凭据暴露给公网客户端。
- 不租用独立公网应用服务器。

### 输入与输出

- 普通用户输入：创建个人空间、访问码恢复请求及现有任务操作。
- 普通用户输出：个人空间 ID、只展示一次并要求保存的访问码、当前空间所属任务及操作结果。
- 管理员输入：管理员凭据、动态验证码、目标个人空间 ID和重置确认。
- 管理员输出：新访问码、旧访问码失效结果及恢复审计记录。

### 可观察成功标准

- 两个不同个人空间在同一套系统中创建任务后，双方均不能读取或修改对方任务。
- 用户可在另一部手机通过访问码恢复同一空间，并看到 SQL Server 中的现有任务。
- 从互联网通过有效 HTTPS 域名访问核心任务功能成功，SQL Server 端口未向公网开放。
- 管理员完成强密码和动态验证码校验后可重置访问码；旧码随即无法使用，审计日志可查。
- 数据库不可用或保存失败时不得虚假显示任务已保存。
