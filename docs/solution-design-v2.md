# Phase 3 技术方案：编排与交付复盘

状态：APPROVED

需求基线：Requirements Baseline v3.0

风险等级：HIGH

设计深度：完整方案。评估命中数据模型、不可逆操作、公共命令入口和跨模块修改；评估结果见 `.project/assessments/phase3-v3.json`。

## 方案目标与范围

- 建立一个只编排既有受控能力、不重新实现业务 Gate 的 `project-orchestrator`。
- 为完成态项目提供受控的新周期入口，并用周期快照保留历史完成事实。
- 默认串行调度；满足依赖、路径租约、语义资源和运行隔离条件时允许并行工作项。
- 建立追加式指标事件与 `delivery-retrospective`，只汇总真实来源，不补造成本数据。
- 首版不接入真实多模型、CI、模板化初始化、真实 Git 工作树和公网部署。

## 总体架构

```text
人工请求 / 周期状态
          ↓
project-orchestrator
  ├─ 周期与契约读取器
  ├─ 下一动作决策器
  ├─ 人工 Gate 防线
  ├─ 幂等动作执行器
  ├─ 工作项调度与资源租约
  └─ 运行/指标事件记录
          ↓
现有受控命令、验证、独立审计
          ↓
delivery-retrospective
  └─ 事实、缺口、偏差、指标、建议
```

- 编排器是协调层，不直接把阶段写成通过；它只能调用白名单中的现有受控入口并验证前后状态。
- 人工 Gate 由版本感知的 Gate 读取器判定，编排器只能返回 `WAITING_HUMAN`，不能产生批准记录。
- 状态判断和调度计算采用纯函数核心；文件读取、命令执行和追加记录放在适配层，便于故障注入和确定性测试。

## 组件与职责边界

| 组件 | 责任 | 不承担的责任 |
|---|---|---|
| 周期注册表 | 标识活动周期、历史周期、版本、阶段和快照引用 | 不复制或改写历史业务文档 |
| 周期启动器 | 校验递增版本、完成态、锁和审计循环，原子启动新周期 | 不自动批准 Gate 1 |
| 契约/Gate 读取器 | 按活动基线定位对应 Gate、方案、计划和交付段落 | 不使用“文件中第一个匹配项”代替版本选择 |
| 下一动作决策器 | 根据状态、前置条件和人工边界产生唯一动作 | 不执行任意 shell 命令 |
| 动作执行器 | 以幂等动作编号调用白名单入口，验证预期状态 | 不跳过失败或改变业务事实 |
| 调度器 | 计算依赖顺序、安全并行组和冲突原因 | 不在信息不足时推断安全 |
| 资源租约器 | 为文件路径、共享接口、共享状态和运行资源分配互斥租约 | 不提供 Git 分支或工作树隔离 |
| 漂移检查器 | 比较批准范围与实际变化，冲突时停止并记录 | 不自动回滚或删除用户修改 |
| 指标记录器 | 追加真实耗时、结果、重试、质量和可得用量/成本事件 | 不估算缺失 token 或费用 |
| 交付复盘器 | 汇总来源、缺口、偏差和建议 | 不自动采纳建议或修改批准产物 |

## 周期与状态模型

- 新增周期注册表，保存项目 ID、活动周期 ID、版本、状态、创建时间和上一周期快照引用。
- 每个周期使用独立目录保存周期元数据、编排动作、指标事件、冲突和复盘索引；既有平铺文档继续作为业务事实来源，不搬迁历史文件。
- 周期快照保存完成时关键产物的路径、稳定编号和 SHA-256 摘要；快照用于证明历史未被改写，不复制密钥或完整环境变量。
- 启动新周期采用临时文件加原子替换：先验证全部前置条件并写入周期记录，再更新活动周期指针和阶段状态；任一步失败均保留原完成周期为活动有效事实。
- v3.0 自举周期保留本次人工启动记录，并在实现完成后通过兼容审计补建周期快照，不伪造自动启动历史。

## 下一动作与自动推进

- 决策结果限定为 `ACTIONABLE`、`WAITING_HUMAN`、`BLOCKED`、`COMPLETED`，并包含动作编号、依据和预期状态变化。
- 人工 Gate 清单固定包含 Gate 1、Gate 2、适用的 UI Gate、技术方案确认、实施计划确认和 Gate 3；清单变化必须通过需求变更。
- 自动动作使用稳定幂等键：周期 ID、当前状态摘要、动作类型和目标共同生成；成功动作再次请求时返回原结果。
- 动作执行前后都运行状态与契约检查；只允许白名单参数化命令，不接受文档中的任意命令字符串。
- 超时、非零退出、状态未达到预期、输出无法解析或人工 Gate 出现时停止，记录最后一致状态与恢复入口。

## 串行与安全并行调度

- 调度器先对依赖图执行稳定拓扑排序；循环依赖直接阻塞。
- 并行候选必须同时满足：无传递依赖、文件路径租约不重叠、共享接口/状态资源不冲突、无全局项目锁竞争、运行时目录可隔离。
- 文件影响范围使用规范化的项目相对路径；拒绝绝对路径、目录穿越、未解析通配符和过宽根目录声明。
- 语义资源单独声明，例如状态契约、公共 CLI、追踪矩阵和数据库结构；即使文件不同，共享语义资源冲突也不得并行。
- 并行工作只写各自声明文件和独立运行目录；中央状态、计划状态、追踪矩阵与最终验证由编排器串行提交。
- 没有真实 Git 工作树时，不自动合并或回滚文件。漂移检查发现越界后冻结受影响租约、停止后续调度并转人工处理。
- 构建、完整测试和 `npm run verify` 使用全局互斥租约串行执行，避免共享缓存和服务端口相互污染。

## 指标事件与复盘

- 指标以每事件独立 JSON 文件追加保存，避免并行写同一日志；事件包含 schema 版本、事件 ID、周期、对象、来源、时间和数据质量状态。
- 时间统一保存 ISO 8601 时间点和非负整数毫秒；次数为非负整数。
- token 分为输入、输出和总量；成本包含金额、币种、提供方和来源。提供方未返回时值为 `null`，并记录缺失原因。
- 质量只引用测试、构建、契约检查和独立审计的真实结果，不根据日志关键字推测 PASS。
- 复盘报告同时输出机器可读摘要和中文 Markdown；分开列出事实、推断、数据缺口和待决定建议。
- 建议具有独立编号和 `PENDING`、`ACCEPTED`、`REJECTED`、`DEFERRED` 状态；只有受控变更或新周期可引用已接受建议。

## 公共命令与接口

- 编排入口提供 `start-cycle`、`next`、`run`、`schedule`、`check-drift` 和 `status`；默认只读命令不得修改项目。
- 修改型命令必须显式提供周期和动作标识，并在项目级编排锁内执行；不开放任意命令透传。
- 交付复盘入口提供 `collect`、`validate` 和 `render`；`render` 只消费已校验指标和业务证据。
- 所有命令使用结构化退出码和中文错误摘要；机器可读输出与用户提示分离。

## 失败处理与恢复

- 编排锁包含动作编号、周期、开始时间和最后心跳；锁存在时禁止第二个修改型编排动作。
- 进程中断后先读取动作日志和前后状态：未产生副作用可安全重试，已达目标则补记完成，状态不确定则进入人工恢复。
- 并行工作失败只取消依赖它的后续工作；同组其他工作是否继续由资源冲突结果决定，不能把失败组标记完成。
- 范围漂移不执行自动删除、覆盖或 Git 回滚；保留现场和摘要，由人工选择修复、接受变更或废弃运行。
- 指标事件错误不修改原运行证据；记录数据质量缺陷，并允许基于原来源重新采集新事件。
- 复盘生成失败不改变 Gate 3 或交付事实，可修复复盘器后重新生成新版本报告。

## 兼容与迁移

- v2.0 及以前 Gate、方案、计划、运行、审计和交付证据保持历史事实。
- 将当前依赖“第一个 Markdown 匹配项”和固定方案文件名的读取逻辑改为按活动周期和基线选择；找不到唯一目标时失败关闭。
- 现有 `.project/state.md` 继续作为活动状态兼容入口；周期注册表成为版本选择来源，二者不一致时停止而非自动修正。
- 现有 `project-control`、工作项控制、审计和契约命令继续作为底层白名单能力；编排器不复制其判定逻辑。
- 当前 v3.0 因编排器尚未存在而采用一次性自举：人工记录周期启动与 Gate，完成后必须用新周期契约进行兼容审计。

## 验证策略

- 纯函数测试覆盖所有阶段状态、人工 Gate、动作唯一性、重复动作和非法状态组合。
- 周期故障注入覆盖无锁/有锁、版本未递增、快照失败、原子更新中断和自举迁移。
- 调度性质测试覆盖传递依赖、循环依赖、路径包含关系、语义资源冲突、稳定排序和保守串行退化。
- 并行夹具覆盖独立范围成功、未声明文件漂移、共享状态冲突、全局验证互斥和人工接管。
- 指标测试覆盖时间与计数校验、未知成本、来源追踪、并发事件写入和不修改原证据。
- 复盘独立样例覆盖完整数据、缺失数据、失败恢复历史和建议不自动生效。
- 项目唯一验证命令继续为 `npm run verify`；独立验收审计覆盖 AC-072～AC-090，并检查受保护实现摘要不变。

# Phase 2 技术方案：工程质量闭环

状态：APPROVED

需求基线：Requirements Baseline v2.0

风险等级：HIGH

设计深度：完整方案。原因是本变更修改阶段状态、受控脚本、Skill 契约、变更失效规则和交付判定，属于跨模块且会影响所有后续项目的工程流程。

## 方案目标

- 在需求确认后、实施规划前增加可分级的方案评估与方案确认。
- 在实施验证后、交付前增加独立验收审计和失败退回。
- 让需求、方案、工作项、测试与证据形成可自动检查的双向追踪。
- 保留 Phase 1 历史事实，并明确 Phase 2 契约从 v2.0 开始生效。

## 目标流程

```text
DISCOVERY → REQUIREMENTS → SOLUTION_DESIGN → PLANNING
→ IMPLEMENTATION → ACCEPTANCE_AUDIT → DELIVERY → COMPLETED
```

- 所有变更进入 `SOLUTION_DESIGN` 评估；低风险允许简化记录，中高风险使用完整方案。
- 实施完成后进入 `ACCEPTANCE_AUDIT`；FAIL 退回 `IMPLEMENTATION`，PASS 才能进入 `DELIVERY`。
- Phase 3 的统一编排器不在本次范围内，阶段推进继续由显式受控命令完成。

## 组件与产物边界

| 组件 | 责任 | 主要产物 |
|---|---|---|
| Phase 2 契约 | 定义阶段、状态、稳定编号和引用格式 | 契约说明、模板、兼容规则 |
| `solution-design` | 风险分级、方案深度、风险登记和方案门 | 方案文档、风险登记、确认记录 |
| 追踪与变更检查 | 双向追踪、悬空引用、下游失效 | 追踪矩阵、影响报告、契约检查结果 |
| `acceptance-audit` | 独立样例、覆盖审计、失败退回和复验 | 审计报告、失败证据、复验记录 |
| 状态控制 | 受控推进和恢复，不承担 Phase 3 编排 | 状态脚本、项目锁、运行与恢复记录 |

## 状态和失败处理

- 新增阶段必须由协议检查器识别，禁止从 REQUIREMENTS 直接跳到 PLANNING，或从 IMPLEMENTATION 直接跳到 DELIVERY。
- 方案的未处理高风险、追踪缺口、契约错误和审计 FAIL 均以非零结果阻止推进。
- 审计不得修改生产实现或实现测试；失败必须关联到待恢复执行工作项。
- 原审计失败记录保持不可覆盖，复验创建新记录并引用原失败和修复运行。
- 检查器自身无法解析必需产物时按失败处理，不降级为警告。

## 兼容与迁移

- v1.3 及以前历史 Gate、工作项、证据和完成状态保持不变。
- v2.0 是 Phase 2 契约的首个生效基线；本方案属于自举产物，后续由新契约进行兼容审计。
- 旧项目只有在明确选择采用 Phase 2 后才要求补充迁移记录，不静默改写历史文件。

## 验证策略

- 自动测试覆盖合法推进、非法跳转、风险阻断、追踪缺口、变更失效、审计失败、修复复验和历史兼容。
- 独立审计样例放在与实现单元测试可区分的位置，至少包含一个故意失败夹具，证明审计能拒绝交付。
- 项目级唯一验证命令继续为 `npm run verify`，并扩展覆盖 Phase 2 契约与审计测试。
